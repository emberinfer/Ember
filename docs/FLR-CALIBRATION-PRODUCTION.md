# FLR 生产标定（入列车前补齐，2026-11-15）

范围：自由层段（pipeline-range-v2）入升级列车前缺的两项标定——(1) GPU 设备对
带宽系数；(2) head 路生产级标定。方法与样本形态沿用 FLR-5 CPU 标定与补测
（/root/flr-calib，CALIB-NOTES.md / CALIB-ADDENDUM.md）及 FLR-7 演练
（FLR-DRILL-REPORT.md）。模型 Qwen2.5-1.5B-Instruct（28 层，BF16，SDPA），
权重 SHA-256 dd924a11b4c220f385b51ffa522daea7c9f3d850e31b162bb5661df483c6d3ee。

机器可读系数见同目录 `flr-range-band-production.json`（即 RangeBandParams 的
JSON 形态，可直接用于创世构造）。要点：**该 JSON 里只有 (cpu,cpu) 一对**，
这是有意的 fail-closed——没有实测系数的设备对不得出现在签名参数里，
链侧 RangeThresholds 对未标定设备对返回 `uncalibrated range device pair`，
审计结论为 inconclusive，而不是套用别对的系数。

## 1. GPU 设备对（2080 Ti ↔ 4090）：fail-closed，无系数

目标生产组合为 684 机 RTX 2080 Ti（生产执行者/审计者各一进程在跑）与
西区 C 机 RTX 4090（vLLM 35B 在跑）。实测结论：**安全窗口不存在，不测、
不给系数**。

- 684（2080 Ti，11,264 MiB）：两个在产 Ember GPU 节点占 10,633 MiB，
  `nvidia-smi` 实测空闲仅 **190 MiB**。探针进程（torch 2.5.1+cu124，
  显存硬顶 4%）仅初始化 CUDA 上下文即占 156 MiB，余 33 MiB；连单个
  解码层权重（约 110 MiB BF16）的分配都 OOM——OOM 只发生在探针自身
  进程内，在产节点未受影响、未重启。此后没有再试：整模型（3.1 GB）、
  逐层流式（上下文+单层 ≈ 266 MiB > 190 MiB）都放不下；把权重切成
  小块拼算会改变核形态，测出的不是生产计算，不作数。
- C 机（4090，49,140 MiB）：vLLM 占 43.9→44.7 GB（运行中 KV cache 仍在
  增长），另有其他线 1.5B 演练进程周期性占 2.5–3.9 GB；空闲在
  0.45–4.65 GB 间波动。等待器（空闲 ≥3.9 GB 持续 30 秒才启动、进程
  显存硬顶 7.4%）多轮尝试：脚本侧两处 OOM 均只杀死自身进程（整表
  FP32 拷贝 892 MiB 撞自设上限，已改分块计算与 CPU 侧权重备份），
  始终没有等到「全程安全」的完整窗口，未挤占、未重启 vLLM 与在产节点。
- 因此 (cuda,cuda) 的 base 与 head_base **不发布**。GPU 段审计在拿到
  任一台机器的真实空闲窗口（建议任一节点下线维护时）按 /root/flr-calib
  同法补测后再签入；在那之前 GPU 对走未标定 → inconclusive 路径，
  与 ValidateRangeBand 的设计一致。

注：RangeBandParams 的 depth_coef 与 hard_multiplier 是全对共享的单一
值，不是逐对的；逐对可签入的只有 base / head_base。若将来 GPU 对拟合出
与 CPU 不同的 depth_coef，需要先扩 proto，不能靠改 JSON 绕过。

## 2. head 路生产级标定（cpu,cpu）：head_base = 0.001

### 方法

沿用演练 head_calib.py 的生产者/参考者双进程形态并扩样：14 条中英提示词
× 10 生成步 = 140 个基样本，前缀长度 39–174 token（演练为 40–54）；
每基样本取 5 个段起点 s∈{0,7,14,21,26} 的 [s,28) 段，共 **700 个 head
实例**。生产者 12 线程、参考者 2 线程，均为 CPU / BF16 / SDPA 独立进程，
段输入逐字节同源（SHA-256 校验），距离用仓库
node/auditor/numeric.py 的 union_distance（top-16 logprobs 并集区间距离）。
脚本与原始数据在 684：/root/flr-head-calib/（head_gen/head_produce/
head_reference/head_fit.py、samples.json、producer.json、distances_*.json、
head-result.json）。

同时测两种语义：

- (a) 演练语义：参考者从同一段输入独立重放 [s,28) 后做自己的 head，
  与生产者终端 top-k 比。与演练 head_base=0.03015（24 样本）同口径。
- (b) 审计真实语义（node/auditor/range_pipeline.py 的 head 路）：参考者
  以自身 norm+lm_head 作用于**生产者承诺的段末边界激活**（FP32 字节
  →BF16 往返校验），与生产者承诺 top-k 比。生产代码实际比较的是 (b)。

### 结果

诚实距离：

| 语义 | n | max | mean | p95 |
|---|---:|---:|---:|---:|
| (a) 独立重放 | 700 | 0.025116041781125645 | 0.007927069908554232 | 0.01813095859563977 |
| (b) 承诺边界 | 700 | 0.0 | 0.0 | 0.0 |

(b) 在同栈（torch 2.5.1 / transformers 4.45.2、线程 12 对 2、全部起点与
长度）下逐位确定，700/700 恰为 0——与演练的 head 隔离边界附测（24 样本
全 0）一致，现扩到生产量级。按演练公式对 (a) 拟合：
head_base_a = max(2×max, 2.5×mean) = **0.05023208356225129**，
hard = 1.2× = 0.060278500274701545；诚实 (a) 全过。

只改 lm_head 的作弊（生产者侧篡改 lm_head 后重算承诺 top-k，参考者按
(b) 以诚实 head 作用于同一承诺边界；层路不受影响，边界本身不变）：

| 篡改 | min | mean | max | 在 (b) 生产线 hard=0.0012 下越线 |
|---|---:|---:|---:|---:|
| ×1.05 缩放 | 0.014459101580537958 | 0.04227504129354777 | 0.059463805104316876 | 700/700 |
| 高斯噪声 σ=0.01×权重std | 0.0017091132375520466 | 0.009268267235872147 | 0.02943321748108904 | 700/700 |
| 高斯噪声 σ=0.05 绝对值（节点测试量级） | 0.23859458258479546 | 0.448847628131712 | 0.6252179844069353 | 700/700 |

### 生产取数与口径

**生产 head_base（cpu,cpu）= 0.001，hard = 1.2× = 0.0012**，按 (b) 真实
审计语义标定。理由：(b) 是生产代码实际计算的量；其诚实噪声在本标定
包络内恰为 0，0.001 是政策下限而非噪声倍数——它比最弱必抓作弊
（σ=0.01std 噪声，min 0.0017091132375520466）低约 1.43 倍（以 hard
计），对其余两类篡改余量 ≥12 倍；诚实 700/700 全过。若改用 (a) 口径的
0.05023208356225129，则 ×1.05 缩放与 σ=0.01std 噪声两类篡改 0/700 越线
（只有 σ=0.05 量级能抓），不满足「只改 lm_head 必抓」。合并线若因跨
CPU 架构未测等理由偏好保守口径，(a) 数值在此备查，但须知其代价。

注意聚合：生产审计对多步请求取 mean 聚合；上表作弊 mean（0.0423 /
0.00927 / 0.4488）相对 soft=0.001 的余量分别为 42× / 9.3× / 449×，
结论在 mean 聚合下不变。跨 CPU 架构、其他运行时版本的 (b) 噪声未测，
head_base 仅对签名指纹钉死的同栈 (cpu,cpu) 对成立。
